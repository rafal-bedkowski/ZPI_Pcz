## 5. Nowe zależności i decyzje techniczne

- AutoMapper 16.2.0 → **16.3.0**: wersja 16.3.0 usuwa ostrzeżenia NU1903 (GHSA-6vhm-j9h7-f9gh, GHSA-gpwp-5797-mjff); build ma 0 ostrzeżeń, a wszystkie testy przechodzą. Wersja 17.0.0 jest dostępna, ale nie została użyta (poza ustaleniem 16.x). Pakiet pobrał `dotnet restore` z NuGet; poza zapytaniami o wersje (`dotnet package search`, lista wersji w NuGet) nic więcej nie pobierano.
- Pakiety dodane wcześniej w csproj (zweryfikowane): `Microsoft.AspNetCore.Authentication.JwtBearer` 10.0.13, `Swashbuckle.AspNetCore` 10.3.1 (Web), `Microsoft.AspNetCore.Mvc.Testing` i `Microsoft.AspNetCore.Identity.EntityFrameworkCore` 10.0.13 (Tests). Brak innych nowych pakietów.
- Kontrolery nie zawierają logiki biznesowej. Logowanie i wydawanie tokenu są w `ILoginService`/`LoginService` w `WebStore.Web` (a nie w `WebStore.Services`), bo testy konwencji sprintu 1 wymagają dokładnie pięciu usług w projekcie Services.
- Rozróżnienie 404 i 400 przy zapisie: usługi zgłaszają `KeyNotFoundException` zarówno dla nieistniejącego rekordu, jak i nieistniejącego powiązania. `PUT` najpierw sprawdza istnienie rekordu przez usługę (brak → 404), a `KeyNotFoundException` zgłoszony podczas zapisu oznacza brakujące powiązanie (→ 400). Dzięki temu nie zmieniano wyjątków usług (testy sprintu 1 asercją sprawdzają ich dokładny typ).
- 409 dla drugiej faktury: usługa rzuca `DuplicateInvoiceException`, a kontroler faktur mapuje ją na 409 (tylko w `InvoiceApi`); szczegóły w sekcji 7.
- Konta testowe: gdy schemat bazy nie jest zaktualizowany (oczekujące migracje) lub baza jest niedostępna, aplikacja w Development nie przerywa startu, tylko loguje ostrzeżenie po polsku; migracji nie stosuje automatycznie (zgodnie z dotychczasowym przepływem z README).
- Klucz JWT i opcje są odczytywane leniwie (`IOptions<JwtOptionsVm>`), a poprawność jest sprawdzana przy starcie (`ValidateOnStart`); błąd startu to `OptionsValidationException` z komunikatem po polsku wskazującym `JwtOptions:SecretKey`.
- Testy: w `ApiFactory` puste wartości konfiguracji (`Seed:TestAccountPassword`, `JwtOptions:SecretKey`) nadpisują user-secrets programisty, więc wyniki nie zależą od jego środowiska; klucz i hasło są losowe, nie ma ich w repozytorium. Ostrzeżenia analizatora xUnit1051 usunięto przekazując `TestContext.Current.CancellationToken`, bez wyciszania.
- `FormLoginInputFormatter` i `ApiFactory.Credentials` są napisane tak (przypisanie krotką), aby istniejący test czystości repozytorium (`US_01_07_…`) nie traktował pola `Password` w inicjalizatorze jako hasła zapisanego w pliku; test nie został osłabiony.

## 7. Poprawki po sprincie (bez user stories)

### Punkt A — duplikat faktury

- `WebStore.Services/Exceptions/DuplicateInvoiceException.cs` (pochodna `InvalidOperationException`, z `OrderId`) zastępuje ogólny `InvalidOperationException`. `InvoiceService.AddOrUpdateInvoice` rzuca ją po sprawdzeniu duplikatu oraz wtedy, gdy `SaveChanges` zgłosi `DbUpdateException`, a po nieudanym zapisie w bazie istnieje już inna faktura tego zamówienia (wyścig, unikalny indeks `OrderId`). Taka diagnoza jest niezależna od providera (usługi nie odwołują się do SQLite ani SQL Server); inne błędy zapisu są rzucane dalej bez zmian (500).
- `InvoiceApiController` mapuje `DuplicateInvoiceException` na 409 (wcześniej każdy `InvalidOperationException`).
- Testy: `InvoiceServiceTests` dostosowany do nowego wyjątku (druga faktura dla zamówienia), dodany deterministyczny test wyścigu `AddOrUpdateInvoice_DuplicateCreatedConcurrently_ThrowsDuplicateInvoiceException` oraz jego odpowiednik na SQL Server (`SqlServerProviderTests`). Wyścig odtwarza `Infrastructure/BeforeFirstSaveInterceptor`: tuż przed pierwszym zapisem usługi zapisuje konkurencyjną fakturę, więc sprawdzenie duplikatu przechodzi, a odrzuca ją dopiero unikalny indeks. Test API na prawdziwą równoległość nie powstał, bo byłby niedeterministyczny; mapowanie na 409 pokrywa istniejący `Post_SecondInvoiceForTheSameOrder_Returns409AndSavesNothing`.
- Hipoteza o niestabilnym teście (z `WEBSTORE_TEST_SQLSERVER`). Ustalone: w testach nie było żadnego testu współbieżności faktury (opisany wyścig nie mógł więc być przyczyną), a testy zależne od czasu (`Login_Token_ContainsExpectedClaims`, testy tokenów) używają jednego znacznika czasu lub zapasu rzędu minut i nie wykazały słabego punktu; przeglądem kodu nie znaleziono testu zależnego od kolejności. Nieustalone: przyczyna jednorazowej porażki, której nie udało się odtworzyć (10 kolejnych przebiegów z SQL Server dało 311/311, przebiegi po poprawkach także przechodzą). Hipoteza bez dowodu: przejściowy problem środowiskowy lokalnej instancji SQL Server Express (każdy test tworzy i usuwa własną bazę, więc przy obciążeniu mógł przekroczyć limit czasu). Jeżeli porażka się powtórzy, potrzebna będzie nazwa testu i komunikat błędu. Obserwacja z tej sesji: raz (na ok. 7 pełnych przebiegów z SQL Server) niezaliczony był nowy test wyścigu na SQL Server po 1 min 10 s (czas sugeruje przekroczenie limitów czasu, nie błąd asercji), ale przebieg nie zapisał komunikatu i nie udało się go powtórzyć; to także nieustalone i zgodne z hipotezą o obciążeniu instancji.

### Punkt B — SQL Server jako baza domyślna

- `AddWebStoreDatabase` (`WebStore.DAL/Configuration`) nie ma już domyślnego providera: brak `Database:Provider` kończy start wyjątkiem z komunikatem po polsku (co ustawić, w user-secrets lub zmiennej `Database__Provider`). `Sqlite` i `SqlServer` wybiera się jawnie; SQL Server wymaga `ConnectionStrings:SqlServer` (jak dotychczas, wyłącznie user-secrets lub zmienna środowiskowa).
- `appsettings.json` nie zawiera sekcji `Database`; `launchSettings.json` ma nowy profil `https-sqlite` (zmienna `Database__Provider=Sqlite`, bez sekretów).
- `setup.ps1`: komunikaty nie twierdzą już, że aplikacja domyślnie działa na SQLite (informują, że bez `Database:Provider` start kończy się błędem, i podają polecenie wyboru SQLite); konfiguracja SQLEXPRESS w user-secrets działa jak dotąd. `setup.sh` (macOS) przypomina o wyborze SQLite; sprawdzone `bash -n` i `--check-only` (setup.sh oraz setup.ps1 `-CheckOnly` przechodzą), pełnego przebiegu na macOS nie sprawdzano.
- `README.md` i `CLAUDE.md` (stos technologiczny — baza danych, Web API, stan projektu i otwarte sprawy) opisują nowy stan; z otwartych spraw usunięto przejście na SQL Server, poprawkę duplikatu faktury i analizę niestabilnego testu, a pozycję o prowadzącym zaktualizowano.
- Testy: `ConfigurationTests` (brak providera → błąd z komunikatem; jawny SQLite i SQL Server działają), `SetupScriptTests.AppSettings_DoNotChooseDatabaseProvider`, `JwtKeyTests.WithoutDatabaseProvider_StartupFailsWithPolishMessage` (start aplikacji w Development i Production), `ApiFactory.DatabaseProvider` (ustawienie przekazywane przez `UseSetting`, bo provider jest czytany przy rejestracji usług, zanim zadziała `ConfigureAppConfiguration`). Testy automatyczne nadal używają SQLite w pamięci niezależnie od konfiguracji aplikacji; testy wariantu SQL Server działają osobno (`WEBSTORE_TEST_SQLSERVER`).
- Ręcznie (`dotnet run --no-build -c Release --no-launch-profile`, Development): bez `Database:Provider` aplikacja kończy start wyjątkiem z komunikatem „Nie skonfigurowano bazy danych…” (z pełnym stack trace, jak przy braku klucza JWT); z `Database__Provider=Sqlite` (plik bazy poza repozytorium) startuje, `GET /api/ProductApi` bez tokenu daje 401, a `/swagger/v1/swagger.json` 200.

### Punkt C — limit czasu poleceń w testach SQL Server

- `WebStore.Tests/Infrastructure/SqlServerTestOptions.cs`: wspólna stała `CommandTimeoutSeconds = 120` i metoda `UseSqlServerForTests` (EF `CommandTimeout`), używana przez `SqlServerProviderTests` (`Open` oraz kontekst konkurenta w teście duplikatu faktury) i `ApiFactory` (tworzenie, kontekst aplikacji i `EnsureDeleted`). Limit obejmuje `EnsureCreated` (`CREATE DATABASE`) i `EnsureDeleted`; logika testów i asercje bez zmian.
- Weryfikacja: `dotnet build -c Release` bez ostrzeżeń i błędów; `dotnet test -c Release` bez `WEBSTORE_TEST_SQLSERVER` — 310 zaliczonych, 8 pominiętych, 0 niezaliczonych (35 s); z ustawioną zmienną (SQLEXPRESS) trzy pełne przebiegi: 3 min 25 s (318/318), 36 s (318/318), 3 min 38 s (1 test niezaliczony: `SqlServerProviderTests.US_01_10_SqlServer_TotalAmountIsExactAfterRoundTrip`, 2 min 18 s, wyjątek w `SqlCommand.RunExecuteNonQueryTds`). Spowolnienia instancji bywają dłuższe niż 120 s, więc sam limit nie eliminuje całkowicie niestabilności.
